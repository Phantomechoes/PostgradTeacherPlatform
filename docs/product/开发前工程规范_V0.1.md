## 0. 规范目标

本规范用于约束项目从正式编码前开始的全部工程行为，使项目具备：**可追踪、可解释、可回滚、可并行协作、可持续维护**的能力。

本项目最高工程原则：

> **先解释，再修改；先小步，再扩展；一个任务一个分支；main 始终可运行；GitHub 是唯一事实源；调研未确认的业务规则不得擅自写死。**

规则强度：
- **必须**：默认不可绕过。
- **禁止**：未经明确批准不得执行。
- **应该**：如需例外必须说明原因。

# 2. 项目角色

## 2.1 项目负责人

负责：产品方向、调研、需求优先级、Issue 是否进入开发、关键方案确认、PR 验收、合并许可、Sprint 推进。

项目负责人**不要求亲自写业务代码**，但每个模块结束后必须能够大致回答：
- 这个模块解决什么问题；
- 数据从哪里进入；
- 经过哪些层；
- 最后存在哪里；
- 修改了哪些文件；
- 如何运行；
- 如何验证；
- 出问题优先看哪里。

## 2.2 Grok 开发 Agent

Grok 是主要编码执行者，不是产品决策者。

负责：检查、解释、实现、测试、文档、验收说明、学习说明。

Grok 无权：
- 擅自改变需求；
- 擅自进入下一 Sprint；
- 擅自选择商业模式；
- 擅自合并 main；
- 擅自删除未知代码；
- 为让测试通过而改变需求含义；
- 擅自升级核心依赖大版本。

## 2.3 GitHub

GitHub 是**唯一事实源（Single Source of Truth）**。

最终必须进入 GitHub：代码、Issue、PR、架构文档、数据库设计、产品决策、调研结论、当前状态、迁移记录、测试结果、版本历史。

# 5. Git 工作流

## 5.1 主分支

仅保留长期稳定主分支：`main`。

要求：
- main 始终可构建、可测试；
- 不直接在 main 开发；
- 禁止 force push；
- 所有业务修改通过 PR 进入 main。

## 5.2 分支命名

```text
feature/<issue-id>-<short-name>
fix/<issue-id>-<short-name>
docs/<issue-id>-<short-name>
chore/<issue-id>-<short-name>
```

示例：
```text
feature/12-project-bootstrap
feature/21-school-model
fix/34-school-search
docs/40-interview-v1
```

## 5.3 一个任务一个分支

一个分支只对应一个主要 Issue。发现新的独立问题，新建 Issue，不“顺手扩大”当前 PR。

## 5.4 开始任务前必须检查

Grok 每次开始任务先做只读检查：

```text
git status
git branch --show-current
git log -5 --oneline
git remote -v
git fetch
```

并汇报：当前分支、工作区是否干净、是否有未知修改、远端是否更新、是否有冲突风险。

若存在来源不明的未提交修改：**立即停止，不得覆盖。**

## 5.5 Git 禁止行为

未经明确批准禁止：
- `git push --force`
- `git reset --hard`
- 删除未知分支
- 直接提交 main
- 随意改写历史
- 覆盖他人工作
- Grok 自行合并 PR

# 6. Grok 强制协议：Explain → Approve → Implement → Explain

这是项目最重要的 Agent 规则。

## 6.1 A：只读检查

任何任务开始时，Grok 先声明：

> “我现在只检查项目状态，不修改文件。”

可检查 Git、目录、相关代码、测试、已有文档。

## 6.2 B：修改前说明

修改任何文件之前，必须输出：

### 【本次任务】
要解决什么问题？

### 【为什么现在做】
为什么属于当前阶段？是否受调研影响？

### 【现有程序位置】
相关代码/目录在哪里？

### 【计划修改】
预计修改哪些文件？每个文件负责什么？

### 【程序流程】
用非代码语言说明数据/请求如何流动。

### 【本次不做】
明确边界。

### 【风险】
可能影响什么？

### 【验收方式】
负责人怎么验证？

### 【检查点划分】
本任务准备拆成几个步骤？

输出后**停止**。只有负责人明确回复“开始”“继续”“按这个方案做”后才能修改。

## 6.3 C：分检查点实施

一个普通任务默认拆成 **2～5 个检查点**。

每个检查点完成后 Grok 必须停止并汇报：
- 刚才做了什么；
- 修改哪些文件；
- 为什么这么改；
- 当前可验证什么；
- 测试结果；
- 下一步准备做什么。

除非负责人明确授权“本 Issue 可以一次性完成”，否则不得跨检查点连续执行。

## 6.4 D：任务完成说明

完成后必须输出：
- 【完成内容】
- 【验收条件】
- 【修改文件】
- 【完整程序流程】
- 【数据库变化】
- 【API 变化】
- 【Windows 如何运行】
- 【如何手动验收】
- 【自动测试真实结果】
- 【本次需要理解的 3 个概念】
- 【已知限制】
- 【建议的下一 Issue】

不得自动进入下一任务。

# 11. 后端分层规则

默认：

```text
API / Router
    ↓
Service
    ↓
Repository
    ↓
SQLAlchemy Model
    ↓
PostgreSQL
```

- Router：接收参数、调用 Service、返回 HTTP 响应。
- Service：业务规则。
- Repository：数据库读写。
- Model：数据库实体。
- Schema：API 输入输出结构。

简单模块允许精简，但必须解释原因。

---

# 12. 数据库规范

- 正式 Schema 以 PostgreSQL 为准；
- 所有 Schema 变化必须有 Alembic migration；
- 禁止手工改正式表后不留迁移记录；
- 可能丢数据的 migration 执行前必须再次确认。

流程：

```text
修改 Model
→ 生成 migration
→ 人工阅读 migration
→ 执行 migration
→ 测试
```

命名：
- 表/字段：snake_case；
- 主键：`id`；
- 外键：`<entity>_id`；
- 时间字段：`created_at`、`updated_at`。

推荐费、SLA、候选数量、试听机制、课时费规则等调研未确认内容，不得写成行业常量。

# 13. API 规范

- 默认业务前缀：`/api/v1`；
- 健康检查：`GET /health`；
- 输入输出使用 Pydantic；
- 错误使用明确 HTTP 状态码；
- Swagger/OpenAPI 可查看；
- 新增业务 API 必须有测试；
- 禁止直接暴露 ORM 的内部/敏感字段。

# 14. 管理后台与小程序原则

## 管理后台

第一阶段后台优先于完整小程序。目标是支撑内部数据管理、调研录入、后续人工影子订单。

原则：先可用，再美化；必须有 loading/error/empty 状态；前端不复制后端业务逻辑。

## 小程序

V0.1 可初始化工程，但不提前实现支付、IM、学生选师、佣金钱包、复杂推荐等未确认流程。

# 15. 测试与验收

每个业务 Issue 至少：
- 正常路径测试；
- 一个关键异常路径测试。

后端：pytest。

修 Bug 必须增加能复现该 Bug 的测试。

“测试通过”必须写真实命令和结果，例如：

```text
pytest
12 passed in 1.83s
```

不得虚构。

---

# 16. 代码质量

Python：Ruff、类型注解优先、函数职责单一、配置不硬编码。  
TypeScript：合理 strict、ESLint + Prettier、避免滥用 any。  
通用：避免过度抽象、复制粘贴、万能 utils、未使用代码、失效注释。

---

# 17. 安全与隐私

## 密钥

- `.env` 只能本地使用；
- `.env` 必须进入 `.gitignore`；
- 仓库仅提交 `.env.example`；
- 禁止代码中硬编码密码/Token/真实数据库口令。

## 敏感数据

当前阶段默认不存储或公开：身份证、完整成绩单原件、未授权联系方式、公司内部敏感资料、未经同意的访谈录音/截图。

未来若做认证材料，需单独设计私有存储、权限隔离、最小化保存、同意记录、删除机制。

日志不得打印密码、Token、完整身份证、完整联系方式、认证材料正文。

---

# 18. 调研与开发联动

任何调研结论必须分为：
- **已验证事实**：可进入产品决策；
- **样本观察**：可以记录，不直接写成行业规则；
- **待验证假设**：进入 `DECISIONS_PENDING.md`。

任何业务 Issue 都必须能够回答：

> “本需求依据哪一条已验证事实或已批准决策？”

没有依据，默认不进入正式开发。

# 22. 必须停止并询问负责人的情况

- 出现未知未提交修改；
- 需要删除数据；
- 需要修改核心架构；
- 需要更换技术栈；
- Issue 与现有代码明显冲突；

- 出现不可逆操作；
- 需要合并 main；
- 需要改变已冻结 V0.1 边界。

# 25. V0.1 冻结声明

从项目负责人确认本规范开始：

1. GitHub 是唯一事实源；
2. main 永远稳定，不直接开发；
3. 一个 Issue、一个主要分支、一个可验收目标；
4. Grok 必须先解释、等待批准，再修改；
5. 默认分检查点推进，每步让负责人知道发生了什么；
6. 代码完成不等于任务完成：测试、文档、解释、验收缺一不可；
7. 调研未确认的业务规则不得写死；
8. Windows 原生是当前主开发环境；
9. 负责人不必亲自编码，但必须逐步理解系统结构和数据流；
10. 任何破坏性、不可逆、越权或范围扩张操作必须停止并询问。

若后续修改本规范，应单独提出 Governance Change，不得在普通业务 PR 中顺手修改。
